问题 A · 三个落点的对比结论

        

          

            落点
            调用面
            判据② 只依赖模型树
            致命伤 / 代价
          

          

            ① 内核 BpmnModel.layoutVertically()
            model.layoutVertically() 写回 shapes/waypoints 私有注册表
            满足
            
              要为布局器开几何注册表的写入口——内部状态外泄;推导代码进内核,模型类继续膨胀
            
          

          

            ② designer 视图层自算
            视图渲染时顺手算坐标,提交前塞回 spec.shape
            不满足
            
              编译合同 / parse→compile 往返 /
              部署冒烟都不经过视图——几何断供;要补就得写回模型,又回到①
            
          

          

            ③ 独立 layout 模块(DiLayout 第二实现)
            compile(model, { diLayout: verticalDiLayout() })
            满足(attach 只读 process 图)
            
              代价:内核唯一必须的改动是 NodeSpec.shape
              改可选(哑坐标反例试过,不成立);块树推导函数须从 layout 模块公开导出供视图共用
            
          

        

        

          倾向:落点③。compiler.ts 的 diLayout
          接缝与注释本就预留了「钉钉式导出换自动布局器」;shape
          可选化后,恒等布局遇缺坐标节点抛错(诚实),竖排布局器成为零视图依赖的第二实现。deriveBlockTree(图→块树)与
          layoutVertical(块树→几何)是两个可独立测的纯函数,视图层(钉钉式递归组件)只消费前者。
        

        
// 成稿后的调用面草图(钉钉式视图 → 导出):

问题 B · 三档 API 手感与 XML 形态

        

          

            档位
            语义
            XML 形态(已部署 + 启动验证)
          

          

            all 会签
            全员同意才通过
            
              非串行多实例 + flowable:collection="approvers" +
              completionCondition ${nrOfCompletedInstances == nrOfInstances}
            
          

          

            any 或签
            任一人同意即通过
            与会签同构,完成条件换 ${nrOfCompletedInstances >= 1}
          

          

            sequential 依次
            按序逐人,全员完成即通过
            isSequential="true" + collection,无完成条件(自闭合元素)
          

        

        
// 候选内核 API(一次调用,三档枚举;元素变量默认 "assignee"):
model.addApprovalTask({
  id: "counter_sign", name: "部门会签",
  collection: "approvers",          // 审批人集合:裸变量名,运行时流程变量注入
  mode: "all",                      // "all" 会签 | "any" 或签 | "sequential" 依次
});

// 固化 vs 覆盖:completionCondition 内核按档固化,不开放覆盖——
// sequential 档传覆盖直接抛错(原型已验证该守卫);真有自定义需求再议,先不给口子。

        

          要点:① per-instance 指派 = flowable:assignee="${assignee}" +
          flowable:elementVariable,已启动实例逐人验证(刘备/关羽/张飞各领一单);② ⚠
          命名空间大坑:Flowable 6.8 引擎读方言属性用
          http://flowable.org/bpmn(引擎常量),官方文档写的
          http://flowable.org/bpm 会让全部 flowable:
          属性静默失联——正式适配器与基准文件正是错误 URI(迭代一遗留,折回修正);③ 非串行档
          isSequential=false 为 XSD 缺省,moddle 序列化按缺省省略(bpmn.io 同款行为,合法)。
        

      


      

        
试过不成立的走法(反例)

        
    
          
  • 
            flowable 命名空间用官方文档的 http://flowable.org/bpm:6.8 引擎读方言属性用 http://flowable.org/bpmn(引擎常量),URI 差一个字母 →
            部署校验报 missing-collection、assignee/elementVariable 运行时全丢,且手写文档原样 XML
            同样失败(与 moddle 无关)。手写同构 XML 双向验证锁定根因。
          
    • 
          
  • 
            loopDataInputRef 纯标准子元素落法:部署通过,但 parse 时文本引用无 id
            可解析 → 往返 compile 后静默丢失集合——破坏内核最高优先级不变量,否决。
          
    • 
          
  • 
            外挂函数建模(不改内核):绕过 addXxx 直接挂 moddle 元素 →
            不在注册表,addSequenceFlow 端点校验直接拒绝;多实例 API 必须进 BpmnModel 方法面。
          
    • 
          
  • 
            哑坐标绕行:建模时传占位 shape + 布局器覆盖 → 调用面骗人,shape
            参数没有意义(本原型的场景就是用哑坐标搭的,别扭感第一手)。
          
    • 
          
  • 
            loopCardinality 表达人数:BPMN 里它是 Expression 元素(非属性,set
            字符串直接序列化崩溃),且拿不到 per-instance 审批人;动态选人只有集合表达式同构。
          
    • 
          
  • 
            分支不收敛的图(分支各自撞
            end):良构检查显式抛错「未良构收敛」——钉钉式画不出这种图,推导宁可拒绝也不出重叠几何。
