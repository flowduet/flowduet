# 支路身份与结构删除修复提案

日期：2026-10-14。状态：待用户确认；本文件不代表生产实现已获批准。

## 1. 目标与证据

修复阶段零的 7 项结构失败，使审批形态转换、删除支路首节点及删除支路开头嵌套块后，存续支路仍保有身份、条件/default 和顺序，为后续对象缓冲与诊断定位提供可靠基础。

证据基线：产品提交 `a72dc9d`；阶段零结果见 [结构基线](system-v1/probes/structure-baseline.md)，可执行合同见 `packages/designer/probes/stage-zero/branch-preservation.test.ts`。当前记录为 7 失败、1 通过，本轮只核对源码和制定方案，没有重新运行或修复测试。

| 失败用例                 | 当前破坏                            | 拟修复行为                               |
| ------------------------ | ----------------------------------- | ---------------------------------------- |
| 单→多，条件分支          | 入/出边重建，条件、名称、顺序丢失   | 原位修改 UserTask，两侧连线完全保留      |
| 单→多，默认分支          | default 引用随入边删除被清除        | 原 default 仍引用原入边对象              |
| 多→单，条件分支          | 入/出边重建，条件、名称、顺序丢失   | 原位移除多实例配置，两侧连线完全保留     |
| 多→单，默认分支          | default 引用被清除                  | 原 default 仍引用原入边对象              |
| 删除首节点，条件分支     | 新 relay 替代支路头，条件和顺序丢失 | 原入边改接后继，删除被移除节点及其出边   |
| 删除首节点，默认分支     | 新 relay 无法承接 default 身份      | 原入边改接后继，default 引用保持         |
| 删除外层支路开头的嵌套块 | 外层头连线重建，顺序翻转            | 原外层入边跨过整块，块内元素与出口边删除 |

已通过的“禁止删除支路唯一节点且模型不变”必须继续通过；同样保留“嵌套块占满外层支路时禁止删块”的守卫。

## 2. 方案选择

推荐：**审批原位转换 + 模型层重定向连线目标 + 受影响 DI 失效**。

其他两条路线不推荐本轮采用：

- 删除后重建同 ID，并复制字段、顺序和 DI：对象引用及生命期仍改变，容易漏掉扩展属性，且旧折线不能直接用于新端点。
- 引入通用图编辑事务、命令栈与局部自动布线：可覆盖更多未来场景，但超出七项缺陷的必要范围；本轮不新增撤销重做或任意 BPMN 图编辑能力。

## 3. 保真合同

### 3.1 身份、属性与顺序

- **转换**：UserTask、两侧 SequenceFlow 均保留原对象与 ID；不经 `removeNode`，不改变这些对象的生命期。
- **删除节点/块并重接**：保留外部入边对象及 ID，只改变其 `targetRef`。真正删除的节点、出口边和块内连线结束生命期，不映射到存续入边。
- 保留入边的 `name`、完整 `conditionExpression` 对象及其属性、扩展内容；不把表达式抽成 body 后重建。
- 源网关不变，因此 `default` 继续指向同一 SequenceFlow；条件与 default 的现有互斥规则不变。删除整个分支时，该分支 default 按原合同清除，不能把“保留支路”套用到“删除支路”。
- 不从 `source.outgoing` 删除再追加存续入边；保留其索引及兄弟支路的相对顺序。
- 不从 `process.flowElements` 删除再追加存续入边；其他存续元素的相对顺序保持。
- 新目标的 `incoming` 加入该入边一次，旧目标的 `incoming` 移除该入边一次；不重复登记、不留下悬空引用。

顺序需区分两层：内存中的 `fork.outgoing` 和序列化使用的 `flowElements`。表单文档恢复会按后者重建引用。本轮同时保持两者已有顺序，不在结构删除时偷偷排序。阶段零嵌套块用例手工 reverse 了 outgoing，它用于验证内存顺序；另外增加两种顺序一致的生产形态夹具验证保存恢复。修复不承诺纠正调用方直接篡改数组造成的既有顺序不一致。

### 3.2 审批原位转换

`convertApprovalToMulti` / `convertMultiToSingle` 保持现有调用签名，操作仍位于 designer；不为了这次修复增加通用任务属性编辑 API。

单→多：先校验节点类型、单入单出、collection/mode/elementVariable 和携带的 formKey；先构造未挂载的 MultiInstanceLoopCharacteristics 及固化完成条件，再一次性写入原 UserTask 的 loop 与 `${elementVariable}` assignee。常量沿用 core，designer 内重复的参数检查可提取私有 helper，与 core 创建合同做一致性测试。

多→单：确认是支持的多实例形态，移除 loop 并清除集合元素 assignee，由用户配置单人审批人；保留任务其余属性、表单绑定、扩展及引用。该 assignee 清空行为与现有产品一致，不能把集合变量当成单人账号。

原位保留不等于允许破坏外部自定义语义：标准循环、非固化完成条件，以及待删除 loop 上额外的 cardinality、数据关联、扩展等非支持内容，均在写入前拒绝转换。`readApprovalMulti` 目前只覆盖部分完成条件检查，实施时补充转换入口的支持形态检查，不能把它视为完整验证器。任务自身未被修改的未知字段继续原样保留。

业务缺项仅在显式 `{ allowIncomplete: true }` 下允许；普通确认、合法格式要求和部署校验不放宽。

### 3.3 模型层安全重接

建议新增一个窄接口：

```ts
retargetSequenceFlow(flowId: string, targetId: string): this
```

接口只改目标，不支持改源或改 ID，职责如下：

1. 在写入前验证 flow、源/旧目标/新目标均属于当前模型，引用与登记一致，目标为流节点；拒绝本接缝不支持的自环。
2. 若新旧目标相同，直接返回，不改变顺序、坐标或对象。
3. 从旧目标 incoming 移除该对象，改 targetRef，加入新目标 incoming；flow 登记表、源 outgoing、default、flowElements 位置不变。
4. 清除该边登记的旧 waypoints，并清理已物化 DI 中对应的 BPMNEdge，避免旧端点残留。

该接口维护图引用与几何一致性；“不得形成空分支”、配对网关和块边界仍由 designer 负责。无新增事件总线或缓冲协议。

### 3.4 两种删除算法

**删除链节点**，例：`fork --fa--> a --at--> tail`：

1. 读完并校验所有端点、单链条件和空分支守卫。
2. 调用重接，将 fa 改为 `fork --fa--> tail`。
3. 删除 a；原出边 at 随之删除，fa 已不再属于 a 的入边，不能被级联删除。

**删除嵌套块**，例：`outerFork --fa--> innerFork … innerJoin --exit--> tail`：

1. 在完整模型上解析块树，预计算块内全部节点、连线及嵌套层级；验证唯一入口/出口、tail 在删除集合外、没有跨边界的非预期连线及空分支风险。
2. 将 fa 改接 tail。
3. 按预计算集合删除块内内容、innerFork、innerJoin 与 exit；不在删除过程的中间态重新推导块树。

统一采用“保留入边”的规则，普通链中段删除和主链删块也适用，不再为这些路径生成 `flow_relay_*` 或 `flow_block_relay_*`。被删除出口边的名称/扩展不合并到入边；它属于被删除的连接关系。审批转换也不再生成 `flow_conv_*`。这不会改变函数返回类型，但依赖自动生成 relay ID 的外部代码需调整，发布说明必须写明。

可预期拒绝全部前置，包括嵌套结构、引用与参数检查；提交阶段是同步的登记/引用更新，不调用宿主回调，不 await。拒绝用例必须验证对象、字段、数组顺序和 DI 均未变。不通过序列化再解析“回滚”，否则会替换存续对象引用。本轮不建设任意外部 moddle 修改的通用事务系统。

## 4. DI 策略与可见影响

模型的几何登记表与 definitions 中已生成的 BPMNDiagram 是两份不同的投影数据。两者都需处理；仅删除登记或重新 attach 图都不足以声称同步完成。

| 操作           | 几何登记表                      | 已物化 BPMNDiagram                    | BPMN 预览                                     |
| -------------- | ------------------------------- | ------------------------------------- | --------------------------------------------- |
| 单↔多转换      | 原 shape、两侧 waypoints 全保留 | 原图保留                              | 原来完整则继续 registry；原来缺失则仍 derived |
| 连线改接新目标 | 只使改接边 waypoints 失效       | 移除该边 BPMNEdge（含其标签）         | 任一坐标缺失后整图 derived                    |
| 删除节点/连线  | 移除对应 shape/waypoints        | 清理指向删除对象的 BPMNShape/BPMNEdge | 不绘制已删除元素                              |
| 重接同一目标   | 完全不变                        | 完全不变                              | 完全不变                                      |

DI 清理由 core 私有 helper 统一执行，接入 `removeNode`、`removeSequenceFlow` 和重接接口。以 bpmnElement 指向的语义对象识别，遍历当前 definitions 的图，不能凭 `${id}_di` 猜测 DI ID；其他流程/对象的图元素保留。兼容当前 compiler 清理的历史 rootElements 图入口。

**明确取舍：删除并重接后，导入图的手工排布可能切换为整图竖排自动布局。** 本轮不拼接两条旧折线、不把箭头留在已删除节点上、不混合原坐标和推导坐标，也不承诺局部保留手工布局。若必须保留手工布局，应另议局部布线能力，不能以复用过期 waypoints 代替。

沿用 `resolveCanvasGeometry` 的整图 fallback，并验证真实宿主通过既有 version/更新路径刷新预览；原位修改对象不能依赖对象引用变化触发重绘。

导出边界：

- 钉钉式导出及 `saveDesignDocument` 已显式使用 `verticalDiLayout()`，继续完整重建 DI，验证无悬空元素且路线到达新目标。
- `compile(model)` 默认仍用 IdentityDiLayout；改接后缺少坐标时明确拒绝，不悄悄改为自动布局。
- 自动布局 attach 只生成 definitions 图，不回填几何登记表。本轮不新增 setShape/setWaypoints，也不宣称一次自动导出后默认 Identity 就能成功。
- `toXML()` 是底层直接序列化，不负责补齐缺失 DI；调用方需要完整布局时走显式 compile。

**关联异常修复**：现有 compile 在验证布局前先 stripDi，Identity 失败会先清掉已有图。将 DI 替换包在限定恢复边界中：保存 diagrams/rootElements 原引用；布局或序列化失败时恢复，成功才保留新投影。测试内置布局失败与序列化拒绝两条路径。该恢复只覆盖 compiler 管理的 DI 容器，不承诺撤销第三方 DiLayout 对语义模型的任意修改，也不新增同一模型并发 compile 的支持。

## 5. 验收与实施边界

确认后将七项红色合同迁入正式回归测试，按以下层次验收：

1. **原始合同**：七项全部转绿；两类空分支拒绝继续保持模型不变。
2. **身份与语义**：节点/连线对象引用、ID、名称、完整表达式、default 引用、出边和 flowElements 相对顺序；转换保留 formKey 与未知任务扩展；支持的 all/any/sequential 三档及显式不完整草稿。
3. **删除边界**：嵌套块的条件/default 两种外层支路、并行块、普通链删除、尾节点与多层嵌套、非法重接拒绝、整个默认支路删除清 default；无孤岛、重复引用及跨块误删。
4. **DI**：完整/缺失/混合 DI 输入；转换几何不变；重接旧路线失效且预览 derived；被删对象不残留在物化图；同目标无操作；Identity 失败保留调用前 DI；显式竖排导出可解析且端点正确。
5. **保存恢复**：从顺序一致的夹具经导出、parse 及设计文档保存恢复，支路顺序、ID、条件/default 和表单绑定保持；反复转换/删除不产生悬空引用或重复 ID。
6. **真实集成**：Playground 带 DI 导入 → 转换 → 删除 → 双视图切换 → 保存重开，验证刷新、顺序和新端点；运行 core/designer/form-create/Playground 正式测试及构建。后续 CI 的 Node 22/24、引擎验证如未实际执行，明确列为未验证，不用本地通过替代。

范围止于 core 图维护、designer 三类操作及其回归测试和说明。不实现工作台缓冲、EntityRef、ValidationStamp、诊断定位或主题改造；保留 fa 能避免本次失效，但同文档删除再复用 ID 的生命期问题仍须阶段零任务 2 的合同另行落实。

实施应从届时最新 develop 建独立修复分支，仅迁入必要合同与修复，不能把整个 prototype 分支作为生产补丁。可按“原位审批转换”“安全重接与删除”“DI 一致性及集成验收”形成可审阅提交；任何中间提交不代表整项验收通过。

本轮停在方案确认。待用户确认上述身份、删除和 DI 取舍后，再据此细化实施清单并开始修复；不在确认前修改生产代码。
