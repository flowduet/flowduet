# 代码审查约定

本约定借鉴 [How the Claude Code team does code review](https://claude.dev/blog/solving-code-review-at-anthropic/) 的分层验证、风险分级和审查收敛方法，适配 FlowDuet 的 GitHub Issues、PR 和现有 CI。目标是节省人的审阅时间，同时不增加验收后缺陷和返工；智能体结论不能代替维护者审批。

## 交付前验证与风险

- 先确定需求、审查范围和可能的失败方式，再选择能实际运行的验证。记录实际命令、结果及未测范围；测试全绿不能否定有反例支撑的发现。
- 按变更行为而非作者或目录定风险：低风险如不改变事实的文案；中风险如常规功能修复；高风险包括 BPMN 解析、编译、往返保真和引擎适配，流程设计文档及表单绑定、恢复，公开 API 与包兼容性，以及依赖、CI 和发版流程。测试或验收记录若改变上述行为的结论，也需按其影响判断，不能仅因是文档而降级。
- 低风险可由实施者自审；中风险及以上应以新上下文独立审查实际补丁，分别核对项目规范与需求。高风险还应做针对其安全及失败方式的专项审查，并由维护者判断证据和剩余风险。工具或独立审查不可用时说明限制，不冒充通过。
- 按变更选择专项检查；适用的全量门槛为 `pnpm lint`、`pnpm test`、`pnpm build`。PR CI 在 Node 22/24 执行这三项及构建产物 ESM 导入检查；`pnpm smoke` 需要 Docker，Flowable 6.8 部署冒烟为本地或手动工作流，并非 PR CI 的一部分。不能以构建、单测或基准文件冒烟代替未执行的实际场景验证。
- 保持 [贡献指南](../../CONTRIBUTING.md) 的 PR 模板、changeset、CI、维护者审阅和发版要求；验证或审查不自动授权提交、推送、合并、发布、真实部署或外部操作。

## 审查对象与发现

- 固定基线和待审提交 SHA；未提交改动则记录基线 SHA 及可复核的补丁快照，包含暂存、未暂存和相关未跟踪文件，不为取快照修改暂存区。对象变化后审查增量及其与原有代码的交互；需要人工确认的变更，在内容改变后重新确认。遵守现有 PR 审批和分支保护规则。
- 每条发现给出文件与行号、触发条件及代码、规格或运行证据；区分重要、细节和既有问题。既有问题不归咎于本次变更，但若影响安全交付，须修复或由维护者明确接受风险。纯风格及工具已覆盖的意见不重复报告；不确定的假设不得当作缺陷。
- 规范和需求的结论分别报告，开头列出各自的重要、细节、既有发现数；无须修复时明确说明。每条发现记录为已修复、误报、有意为之或不值得改，后三项附理由；未关闭的重要发现不得宣称完成。

## 审查收敛

- 一轮是针对同一审查对象的一组审查：并行或接连进行的规范、需求及专项审查算同一轮；修复后再次审查算新一轮。
- 第 1 轮审查完整补丁，高风险变更的第 2 轮也审查完整补丁；之后审查新增差异及其交互，带上已报告发现清单，避免重复。增量审查暴露新的系统性风险时，扩大审查范围，不因轮次限制忽略真实问题。
- 同类问题按问题类别报告并核查受影响范围，尽可能一次修完所有已确认实例，不只修被指出的一行。
- 第 3 轮后仍有重要发现时暂停循环，说明原因与备选路线，由用户或维护者决定重新审视方案或调整范围；确认新路线后重新计审查轮次。涉及范围扩大或追加投入时，按[可视化决策约定](workflow.md#范围与投入决策)先展示取舍再批准；审查轮次重计不清零同一问题的累计投入。方向性异议尽早在需求或方案阶段提出。

## 交付与复盘

- 中、高风险交付先给简短决策摘要（建议不超过 15 行）：风险、审查对象和各类发现数、实际验证结果、检查会漏掉什么、回退或恢复方式及是否需要人工决定。详细证据放在现有 Issue、PR 或验证记录中；无法验证回退时说明原因和风险，不把计划写成实测。
- 保持变更小而可回退。迁移、格式或公开包兼容性等变更须说明受影响数据或调用方的恢复路径；npm 版本不撤包、不复用，按贡献指南处理发布。
- 验收后发现的缺陷记录漏检层次和原因，修复时补回归测试；复盘审查轮数和发现的处置结果。反复出现的问题优先固化到适用的测试、检查或项目规范，而非重复增加审查意见。
