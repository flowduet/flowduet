# 开发工作流

本项目以 Matt 的 [Ask Matt 流程图谱](https://github.com/mattpocock/skills/blob/main/skills/engineering/ask-matt/SKILL.md) 为流程来源。执行某一步时读取当前安装的对应 `SKILL.md`；本文件记录项目适配，不复制上游技能全文。技能调用范围与冲突处理见 [skill-policy.md](skill-policy.md)。

## 进入任务

1. 读取 `AGENTS.md` 要求的资料，检查当前分支、工作区和有关服务状态。续做已有任务时先核对既有规格、决策、提交和验证证据，保留用户未提交的改动。
2. 用一句话说明本轮目标、所处阶段和下一项完成条件。问题由仓库事实能回答时先查证；只有用户能决定的取舍才提问，已确认且未变化的决定直接沿用。
3. 按下表选择入口。用户已明确调用某技能时使用该入口；若它与任务或既有确认冲突，指出具体差异，再确定适用路线。只读咨询、审查和文档维护按实际范围处理。

| 情况                                     | 路径与阶段产物                                                                                                         |
| ---------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 新想法或需求含糊，规模能在一次讨论中把握 | `grill-with-docs` → 明确问题、范围、用户行为和关键取舍；已确定的领域术语进入 `GLOSSARY.md`，符合条件的长期决策才记 ADR |
| 对话无法决定的状态逻辑或交互             | `prototype` 验证一个具体问题 → 将结论和原型指针带回讨论；跨目录交接按 `handoff` 保留指针                               |
| 明确且一个上下文能完成的变更             | `implement` → 在已确认测试入口按 `tdd` 实施 → 验证 → `code-review`                                                     |
| 需要多个实施上下文的功能                 | `to-spec` 确认测试入口并形成规格 → `to-tickets` 确认可独立验证的切片及阻塞关系 → 按依赖逐票 `implement`                |
| 外部原始缺陷或功能请求                   | `triage` 核实、分类并形成可执行简报 → 对应开发路径；`to-tickets` 产出的票不重复 triage                                 |
| 难复现缺陷或性能回退                     | `diagnosing-bugs` 先得到能捕捉原始症状的反馈循环 → 缩小复现、检验假设 → 修复与回归 → 重新验证原始场景                  |
| 巨大且方向不清的工作                     | `wayfinder` 收敛决策和范围 → 地图清晰后进入 `to-spec`、`to-tickets`；地图阶段本身不交付产品实现                        |
| 文案、配置或机械改名，不改变产品行为     | 直接确定补丁范围 → 专项检查 → 按风险审查；无需为了流程增加无意义的业务测试                                             |
| 开发结束，尤其出现漏检、返工或反复失败   | `retro` 找出环境、检查或规范的改进候选；由任务授权决定是否另外实施                                                     |

### 用户触发的阶段入口

`ask-matt`、`grill-with-docs`、`to-spec`、`to-tickets`、`implement`、`implement-spec`、`triage`、`wayfinder`、`handoff`、`retro` 在上游声明为仅由用户调用（`disable-model-invocation: true`）：阶段推进由用户决定，代理的技能清单通常看不到它们。

- 用户以 `/技能名` 或在请求中点名调用时，按该技能执行。
- 判断任务应进入上述入口而用户未调用时，说明所处阶段、理由和建议输入的命令（如 `/grill-with-docs <主题>`），然后停下等待；不自行读取其 `SKILL.md` 代为执行，也不以临时流程替代该阶段。用户明确要求跳过该入口时按指示执行，并在交付说明中注明未经该阶段。
- 已进入的阶段内，可按该技能要求调用由模型触发的技能，如 `tdd`、`code-review`、`grilling`、`domain-modeling`、`pr`；“文案、配置或机械改名”路径不需要阶段技能。
- 技能升级后核对各 `SKILL.md` 的 frontmatter，名单变化时同步本节。

## 确认与实施

- 架构调整、数据迁移和核心逻辑变更，先给出可审阅提案，确认后实施。已有授权覆盖的步骤持续执行，不重复请求确认。
- `to-spec` 确认测试入口；`to-tickets` 确认切片粒度和真实阻塞关系。每票说明用户可观察行为、验收条件和范围；大范围机械迁移按上游的扩展、迁移、收缩路径处理。
- 写行为测试前，列出已确认的公开测试入口及其能捕捉、不能捕捉的失败方式。已批准规格中的测试决定可作为确认依据；入口变化时重新确认。
- 按 Matt 的 `tdd` 一次推进一个失败测试和最小实现，实际观察失败后再修复。测试通过公开接口验证行为，期望值来自规格或独立样例。重构放在审查阶段，修复后重新运行相关检查。
- 实施前从最新 `develop` 创建符合 [贡献指南](../../CONTRIBUTING.md#分支与提交) 的分支。续做同一已隔离任务时核对基线并沿用分支，避免把已有未提交工作带入无关任务。
- 默认逐票实施，每张票使用独立的新上下文；先前聊天只作线索，工单必须足够自包含。需求讨论到拆票尽量保持连续；容量不足时在阶段边界压缩并保留来源指针，不能假定平台一定支持 `/clear` 或关闭自动压缩。

## 并行实施

`implement-spec` 是显式选择的路线。开始前确认整份规格、任务图、集成分支和工单收尾方式；每票使用独立子代理、分支及工作树，并以集成分支实际提交为基线。不得重置用户已有工作。

普通逐票实施按 GitHub 原生阻塞关系安排顺序，由维护者合入和处理工单后解锁后续票。已授权的同一集成分支内，可依据前置票已验证并集成的提交 SHA 推进任务图，记录对应证据；这不等于关闭 GitHub 工单，也不解除其他开发路线的阻塞。

审查技能按自身要求使用独立上下文，不等同于授权并行实现产品功能。工具不可用时报告限制，不能将自审写成独立审查通过。

## 验证、审查与交付

1. 开发过程中运行针对性类型检查和测试；行为代码实施结束运行完整测试套件。其余适用门槛、风险分级、独立审查和收敛规则遵循 [代码审查约定](code-review.md) 及贡献指南。
2. `code-review` 固定基线和实际补丁，分别报告 Standards 与 Spec。未提交工作按项目约定保存包含新增文件的可复核快照；规范审查同时读取项目审查约定。记录每项发现的处置和修复后的实际验证结果。
3. UI 行为、BPMN 导出或部署承诺需要各自场景证据。单测、构建和基准文件冒烟不能替代浏览器或真实引擎验收。说明未执行项和原因；纯文档改动说明全量测试不适用的依据。
4. 本地提交服从本轮任务授权和约定式提交规则。验证或审查通过本身不增加授权；实施票的完成评论内容见 [issue-tracker.md](issue-tracker.md)。
5. 推送、开 PR、合并和发布遵循既有逐项授权，已有明确授权不重复询问。PR 使用仓库模板；维护者审阅及 CI 门槛保留。实施完成时不关票，关票由合并流程核对处理。
6. 交付说明实际行为、验证结果、未测范围及剩余事项。未完成时指出停在哪一步、由谁对哪个对象做什么、满足何种条件继续；只有建立了后台执行机制，才承诺自动跟进。

## 规则维护

机械规则优先进入现有 linter、测试、Git hook 或 CI；需要判断的规范进入适用文档。规则改动、技能升级和新插件启用后，按 [隔离验证记录](workflow-isolation.md) 重做配置及场景检查。CI 能验证产物和检查结果，不能证明一次访谈或思考过程完整发生。
