# Spec：抄送节点（服务任务 + 适配器扩展属性）

- 状态：**成稿**（2026-09-20；grilling R3 决策折入，拆票依据）
- 域术语：CONTEXT.md「抄送」
- 上游约束：ADR-0004（不在模型层发明 BPMN 之外私有节点类型；特色能力经适配器扩展属性落地）

## Problem Statement

审批流里高频的「知会」没有建模手段：配置者想让某些人在流程推进时收到通知但不阻塞流程。当前内核没有抄送节点，宿主只能绕过设计器手工拼 XML。

## Solution

模型层新增抄送任务：经**引擎中立任务映射**落成 `bpmn:ServiceTask`，收件人经**适配器扩展属性**承载，知会行为由宿主绑定的 delegate 实现——适配器合同「扩展属性注入点」的首个真实消费者。

## User Stories

1. 作为审批流配置者，我想添加抄送节点并选收件人，这样相关人知悉流程进展但不产生待办。
2. 作为审批流配置者，我想抄送不阻塞流程，这样它不会被「审批」卡住。
3. 作为宿主开发者，我想用中立的 `addTask("cc", …)` 建抄送，这样换引擎时调用面不动。
4. 作为宿主开发者，我想收件人支持字面量列表与运行时表达式，这样静态名单和发起时选人都覆盖。
5. 作为宿主开发者，我想绑定一个 delegate 实现站内通知，这样知会行为在我手里而非内核里。
6. 作为适配器作者，我想抄送收件人进入扩展属性 schema，这样合同测试有真实负载而非人造用例。
7. 作为 Flowable 运维，我想含抄送的 XML 部署通过，这样占位 delegate 引用不阻止部署注册。
8. 作为内核嵌入开发者，我想导入的抄送 XML 再导出等价，这样往返保真不破。

## Implementation Decisions

- **API 入口**：`addTask("cc", { id, name?, recipients })` 走既有引擎中立路径（grilling R3）；适配器 `taskTypeMapping` 新增 `cc` 项：`bpmn:ServiceTask` + 方言属性。不设专用方法（与多实例不同，抄送无登记表依赖，中立路径够用）。
- **收件人属性**：单属性 `flowable:ccTo`，值为字面量逗号分隔或运行时表达式（多值不拆多属性——XML 属性单值）。
- **执行承载**：方言固定写**占位 delegate 引用**（约定 bean 名，宿主绑定实现知会）——对齐 ADR-0004「知会行为由宿主实现」。部署合法不要求 bean 在场；执行到该节点需宿主提供 bean（文档明示此合同）。
- **Mail 任务形态否决**（迭代二规划决策）：`flowable:type="mail"` 绕开扩展属性注入机制，且把站内知会心智绑死在邮件语义。
- 模型层语义是「抄送」，方言层是 ServiceTask——语义/方言两层分离与既有任务建模一致。

## Testing Decisions

- **适配器合同**：扩展属性注入点新增 `ccTo` 的真实消费者断言（三要点合同测试扩展——这是注入点第一次有业务负载）。
- **编译合同**：含抄送的基准文件（占位 delegate 引用 + `ccTo`，含 bpmndi）逐字一致。
- **往返保真**：`ccTo` 属性与 delegate 引用 `parse → compile` 保留。
- **冒烟**：6.8 部署注册断言；执行语义（绑定 bean 后知会）文档化给宿主，不进冒烟（本地无宿主 bean，与迭代一「部署是底线」口径一致）。
- 先例：flowable 适配器合同测试的三要点断言。

## Out of Scope

站内通知的实现、抄送时机策略（进入节点即抄 vs 完成后抄）、抄送范围表达式语言设计、条件抄送、多次抄送去重。

## Further Notes

扩展属性 schema 落描述符时与多实例的 `collection`/`elementVariable` 一并进适配器扩展包——一次描述符变更服务两个 spec。
